# spec-to-agent

Turn one frozen specification into one agent version.

You are invoked by an operator who has already reserved the version. You do not choose which spec
to build, you do not choose the version number, and you do not decide whether the result is good
enough to activate. Those are all decisions the operator has already made or will make after you
finish. Your job is narrow: read the spec, write five files, prove they work, and hand back.

## Before you start

The operator gives you an `agentVersionId`. Everything else you derive from it.

```bash
pnpm agent:export-spec --agent-version <agentVersionId>
```

This writes the frozen spec to `.meridian/specs/<specHash>.json` and prints the reserved
`code_path`, the `spec_hash`, and the capabilities the version is allowed to use. Read the spec
**only** through this command. Do not query the database, and do not read `frozen_specs` through
any other path: the export is what pins the hash you are about to record.

Verify that the `spec_hash` printed by the export matches the one in the operator's request. If it
does not, stop and say so. A mismatch means the version was reserved against a different spec than
the one you are being asked to implement, and generating anyway would produce a version whose
recorded lineage is a lie.

## What you may write

Exactly these five files, all inside the reserved `code_path`:

| File                 | Contents                                                                  |
| -------------------- | ------------------------------------------------------------------------- |
| `agent.ts`           | The `AgentDefinition` export: input schema, decision schema, and `run()`. |
| `rules.ts`           | Pure policy functions. No I/O, no clock, no randomness.                   |
| `prompts.ts`         | Every string the agent sends or asks.                                     |
| `manifest.json`      | The build manifest (see `references/agent-contract.md`).                  |
| `spec.snapshot.json` | The exported spec, byte-for-byte.                                         |

You may not create, edit, move, or delete anything else. In particular:

- **Never** edit the frozen spec, `spec.snapshot.json` aside from copying the export verbatim, or
  any file under `supabase/`.
- **Never** edit the shared runtime (`packages/core`, `packages/agent-kit`, `packages/ops`,
  `apps/**`). If a contract you genuinely need does not exist, stop and report exactly what is
  missing. Adding it yourself would put untested runtime behaviour inside a generated version,
  where nobody reviews it as runtime code.
- **Never** edit a previously generated version's folder. Repairs get their own version; see the
  `eval-repair` skill.
- `generated-agents/index.ts` is regenerated by `pnpm agent:finalize`. Do not hand-edit it.

## The contract the code must satisfy

Read `references/agent-contract.md` in full before writing `agent.ts`. The short version:

- Import from `@meridian/agent-kit/contracts` and `zod`, and from your own sibling modules. Nothing
  else. No `@supabase/*`, no `openai`, no `@composio/*`, no `node:*`.
- No `Date.now()`, no `new Date()`, no `Math.random()`, no `setTimeout`. Use `context.clock`.
- Reach the outside world only through `context.toolRegistry`.
- Record every step through `context.recorder`, using a stable `stepInstanceKey`. `sequenceNo` is
  display ordering and nothing else.
- Every external effect goes reserve → dispatch → complete, with the provider call strictly between
  dispatch and complete.
- Return a value that parses against the decision schema. Do not throw to signal a business outcome;
  an unhandled case is `manual_review`, not an exception.

## Verify before you finalize

```bash
bash .codex/skills/spec-to-agent/scripts/verify.sh
```

This runs lint, typecheck, the unit suite, and one smoke eval case. All four must pass. Do not
proceed on a partial pass, and do not weaken a check to get past it.

## Finalize

```bash
pnpm agent:finalize --agent-version <agentVersionId>
```

This regenerates the registry, commits only the allow-listed paths, re-reads the commit out of the
Git object database to confirm it contains what it claims, re-runs the manifest's validation
commands, and records the SHA. If it refuses, read the refusal: it is telling you about a real
difference between what you wrote and what got committed.

## When to stop instead of proceeding

Stop and report, rather than guessing, when:

- The spec does not decide something the agent must decide. That is a policy gap. Say which
  decision is undefined and which node you looked at.
- A required contract is missing from `@meridian/agent-kit/contracts`.
- The export's `spec_hash` does not match the operator's request.
- `verify.sh` fails for a reason inside the shared runtime rather than inside your five files.

Stopping with a precise question is a successful outcome. Inventing business policy to make a suite
green is not.
